# Скорость и GPU

Подготовка грунта и распространение волн — разные этапы. `init` создаёт случайные поля, геометрию и экспорт. `run` выполняет FDTD для каждой позиции. GPU ускоряет поддерживаемую часть решателя; это не гарантирует ускорение всего опыта.

## Выбор устройства

```bash
python geodatagen.py backends
python geodatagen.py run park-demo --backend cpu --limit 1
python geodatagen.py run park-demo --backend metal --limit 1
```

По умолчанию используется CPU. `metal` предназначен для Apple Silicon и требует доступной сборки решателя с Metal. `cuda` — для поддерживаемого NVIDIA GPU, CUDA Toolkit и зависимостей CUDA в gprMax. Явный выбор неподдерживаемого устройства завершится ошибкой. `auto` выбирает доступное устройство, но не измеряет его скорость.

Зависимости GPU устанавливаются отдельно:

```bash
bash scripts/setup-gpu.sh metal   # Apple Silicon
bash scripts/setup-gpu.sh cuda    # NVIDIA + установленный CUDA Toolkit
```

После установки повторите `backends` и численное сравнение.

## Измерить на своей сцене

```bash
python geodatagen.py benchmark park-demo --backends cpu metal --traces 1
```

Команда сравнивает устройства на копии опыта и сохраняет отчёт в `experiments/park-demo/benchmarks/`. Исходные рассчитанные трассы не заменяются. Проверяйте не только время, но и относительное отличие сигналов: быстрый расчёт с другим результатом не считается подтверждённым ускорением.

## Результат проверки

На Apple M5 для одной позиции, окна 1.2 × 1.2 × 1.2 м и источника 600 МГц получены такие времена полного запуска:

| Сцена | CPU | Metal | Относительное L2-отличие |
| --- | --- | --- | --- |
| Модель полей, окно полной сцены парка | 17.32 с | 37.39 с | 0.00001996 |
| Небольшой пример Peplinski | 2.19 с | 6.76 с | 0.00000892 |

В этих опытах Metal медленнее CPU. Поэтому CPU оставлен основным вариантом. Численное расхождение ниже выбранного инженерного порога 0.0001; это проверка согласованности реализаций, а не доказательство сходства грунта или прибора с реальностью. На более крупных задачах соотношение может измениться. [Условия и результаты измерений](../assets/benchmark.json).

## Что ускорено при подготовке

Устранено повторное построение кэша шрифтов Matplotlib при каждом новом `init`. В небольшом примере `smoke.json` подготовка геометрии при уже заполненном общем кэше заняла:

| Генератор | Раньше | Теперь |
| --- | --- | --- |
| Peplinski | 8.805 с | 0.665 с |
| Модель полей | 8.718 с | 0.697 с |

Это медианы двух повторов: ускорение примерно в 13 и 12.5 раза. Первый запуск с пустым кэшем всё ещё занял 9.57 с. Измерялась подготовка геометрии без FDTD, HTML-предпросмотра и расширенного NumPy-экспорта, поэтому весь `init` не обязан ускориться во столько же раз. Индексы и свойства материалов, а также непрерывные поля при сравнении совпали точно.

Извлечение локального окна объединено с преобразованием сетки: один и тот же глобальный объём не требуется заново целиком читать и измельчать для каждой трассы. Медиана замера этой операции уменьшилась с 0.01805 до 0.00463 с, примерно в 3.9 раза. Это ускорение подготовки массива, а не всего FDTD-расчёта.

Геометрия и материалы сохраняются с контрольными суммами. Подготовленные окна используются повторно; повторный `run` пропускает готовые позиции.

## Размер задачи

Уменьшение `solver_dx` вдвое увеличивает число трёхмерных ячеек примерно в восемь раз и требует меньшего временного шага. Полная стоимость растёт быстрее, чем размер геометрии. Увеличивать шаг сетки или сокращать время записи нужно с проверкой влияния на сигнал.

Для больших сцен движущееся окно ограничивает память. Оно извлекается из сохранённого глобального грунта. Увеличение окна улучшает охват отражателей, но увеличивает время и память. GPU не компенсирует отражения, которые исключены границами окна.
